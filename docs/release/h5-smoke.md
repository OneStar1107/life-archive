# H5 全量无头巡检（17 页 × 双主题）

> **一句话**：`node frontend/scripts/smoke-pages.mjs` 一条命令，把「页面渲不渲染得出来、深色下有没有透白、
> 控制台干不干净」跑成一份可复现的报告，而不是靠人肉翻页面。
>
> 脚本本体：`frontend/scripts/smoke-pages.mjs`
> 所属文档组：`07-三端测试体系`（H5 侧的自动化补充）

---

## 一、它检查什么

对**每个页面 × 每个主题**独立判定，共 34 项（17 页 + 2 次冷启动）：

| 断言 | 失败含义 |
|---|---|
| 无 `[PAGEERROR]` / console error | 页面 JS 崩了（典型：模板里用了未 import 的东西） |
| 无 `[http4xx/5xx]` / `[reqfail]` | 接口挂了。**明细带 URL**，不用猜是哪个请求 |
| 根节点高度 ≥ 视口 60% | 页面没铺满，疑似白屏 |
| 可视文本 ≥ 10 字 | 疑似空白页 |
| canvas 有非零位图尺寸 | 画布没被正确初始化（记忆页图谱的回归项） |
| **深色：无中性亮色横带/面板** | dock 透白、忘上面漆。详见第三节 |
| 冷启动零 error | 启动路径不要有噪声，否则会掩盖真问题 |

产物流到 `.workbuddy/tmp/smoke/`：

- `report.json` —— 结构化结果
- `{theme}__{页面路径}.png` —— 每页截图，**用于人工目检**

## 二、怎么跑

### 前置

1. HBuilderX 已把 H5 跑起来，默认 `http://localhost:5173`
2. 后端已启动，**且跑的是当前代码**（默认 `http://127.0.0.1:3000`）
3. `puppeteer-core` 可解析

> ⚠️ **第 2 条最容易踩坑**：H5 走同源请求，由 `manifest.json` 代理转发到后端 `:3000`。
> 如果你改了后端但**没重启 3000 上的实例**，页面会命中旧逻辑，表现为一堆莫名其妙的 400。
> 本仓库上次就是这么误判了一次「洞察页有 bug」，实际后端早修好了。
> 判断方法：`curl -s --noproxy '*' "http://127.0.0.1:3000/<接口>"` 看返回是否为新逻辑。

### 依赖

`puppeteer-core` **故意不装进项目依赖**，避免污染 uni-app x 的依赖树。装在项目外：

```bash
cd <某个项目外的目录> && npm i puppeteer-core
```

然后三选一告诉脚本去哪找：`--pptr <目录>` / `SMOKE_PPTR=<目录>` / `NODE_PATH=<目录>`。

> 📌 **ESM 的 `import()` 不认 `NODE_PATH`**，脚本内部是用 CJS 的 `require.resolve(..., {paths})`
> 先定位入口再 `import` 绝对路径绕过去的。这是有意为之，别「简化」掉。

### 命令

```bash
# 全量
NODE_PATH="<含 node_modules 的目录>" node frontend/scripts/smoke-pages.mjs

# 只跑某几页、只跑深色、不看截图
node frontend/scripts/smoke-pages.mjs --only pages/todo/index,pages/insight/index --theme dark --no-shots

# 指定后端 / dev server
node frontend/scripts/smoke-pages.mjs --base http://localhost:5173 --api http://127.0.0.1:3100
```

**退出码**：`0` = 全通过；`1` = 有 FAIL；`2` = 环境不可用（浏览器起不来 / 后端登不进）

## 三、深色白块检测是怎么工作的

这是整套巡检里最容易做假的部分，也是踩过坑最多的地方，所以单独说明。

### 判定标准：「中性亮色」

```
亮度 > 0.5  且  chroma（RGB 通道极差）≤ 30
```

**chroma 这道过滤是必须的**。只按亮度判的话，深色页底部一个正常的主色按钮
`#7FD4F2`（亮度 0.77）就会被判成「透白」。加了 chroma≤30 之后：
白/灰/黑（chroma≈0）才报警，品牌色（chroma 115）放行。

### 两条路并行，缺一不可

| 路径 | 抓什么 | 为什么必须有 |
|---|---|---|
| **A · 全视口网格点采样**<br>11 列 × 每 12px 一行，扫整个视口；某行 ≥60% 采样点为中性亮色记为 hot row，连续 ≥2 行（≥24px）才报警 | 「**没人画**，于是露出白色画布」 | dock 透白的真实成因就是这个。而且**不能**改成枚举元素：`<html>` 自己不画任何东西，但祖先链合成结果就是纯白，枚举元素会把整页误判成白块（实测踩过，17 页全 FAIL 报 `HTML 390x844 rgb(255,255,255)`） |
| **B · 元素枚举**<br>遍历元素，要求**自己确实画了东西**，可见面积 ≥8000px²，且为中性亮色 | 「**画了**，但画成了白的」 | 抓具体的 `#ffffff` 块、白色 `linear-gradient`、`::before` 上的白底 |

### 为什么 `backgroundImage` 和伪元素都要查

一个元素的底色有三条渲染路径，只查 `backgroundColor` 会漏掉两条：

- `background-image: linear-gradient(#fff, #fff)` —— 此时 `backgroundColor` 往往仍是全透明
- `::before` / `::after` 伪元素画的底

渐变的色值字面量要能从 `rgb()/rgba()` **和** `#rgb/#rrggbb/#rrggbbaa` 两种写法里解析出来。
解析不了的（多为 `url()` 背景图）**不当 FAIL**，单列成 `warnPanels` 交给人工确认——
宁可漏报也不拿图片背景当白块误伤。

### 为什么必须做 alpha 合成

卡片底色是 `rgba(255,255,255,0.07)`。直接拿 RGB 通道算亮度会得到「纯白」的**假阳性**，
实际叠在 `#081217` 上只有约 0.1 的亮度。做法是从元素往上收集所有非透明背景层，
再从浏览器默认白底开始逐层合成，得到人眼真正看到的颜色。

### 这套检测器的来历：mutant 测试

它是在**注入式反向验证**下长出来的。做法是人为往页面里塞各种形态的白块，看检测器报不报。
第一版漏了 4 类（`gradient` 白块、`::before` 白块、落在采样盲区的 40px 高白带、
小于尺寸门限的 190×49 白块），加固后这些全部被抓到，同时真阴性（0.07 白叠深色、
主色按钮）不误报。

**以后改这套判定，必须重跑 mutant 矩阵**，不要凭手感调阈值。

## 四、已知边界

- **只覆盖 H5**。iOS / Android / 鸿蒙三端没有对应的无头链路，仍走 `docs/release/test-matrix.md` 的真机矩阵。
- **没接进 `check:all`**：因为它依赖运行中的 dev server 和后端，不能放进纯静态门禁。
- **截图要目检**。脚本已尽量避免「数字全对但截图里明显一块白」的情况（这是本项目交过学费的坑），
  但数字与截图的**同场对照目检**仍然是最后一道保险，尤其改了主题变量之后。
